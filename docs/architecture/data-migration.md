# Advisors Club — Production Data Migration

Target: `UI → existing store → repository → Supabase`.
The UI is not rewritten. Stores keep their current synchronous, event-based API.

## The three layers

| Layer | Files | Rule |
| --- | --- | --- |
| Backend switch | `src/lib/data/backend.ts` | One flag per domain: `local` or `supabase`. Flip a domain only after its repository is implemented and verified. |
| Repository | `src/lib/data/repository.ts` + `src/lib/<domain>/repository.ts` | Async, tenant-scoped CRUD. `CollectionRepository` for lists, `DocumentRepository` for one-doc-per-club. |
| Cache bridge | `src/lib/data/cache.ts` | Keeps localStorage as first-paint cache; `writeThrough()` mirrors mutations to Supabase without blocking the UI. |

Tenancy is resolved in exactly one place: `src/lib/clubs/context.ts`
(`activeClubId()`, `requireClubId()`, `resolveActiveClub()`). No repository
invents a club id. Until a real club is selected, `activeClubId()` returns the
prototype id `"default"` and every domain stays local.

## Store migration recipe (used for Apps and Navigation)

1. Add `src/lib/<domain>/repository.ts` — the interface only.
2. Add `src/lib/<domain>/supabase-repository.ts` — row mapping in/out.
3. In the existing store: add `remote()`, a `hydrate<Domain>()` reader, and a
   `writeThrough(...)` call inside each mutation. Public API unchanged.
4. Flip the domain in `backend.ts` once verified.

## Inventory and migration order

Status: `done` = repository implemented, `next` = ready to start.

| # | Domain | Store today | Supabase tables | Repository | Backend |

| 7 | Coaching | `src/lib/coaching/*` | `coaching_programs`, `coaching_sessions` | next | local |

Order rationale: tenancy first (nothing else can be scoped without it), then
the two smallest single-document domains as pilots, then content, then
commerce (which depends on content ids), then AI (which references everything).

## Rules for every future domain

- Ids are stable UUIDs generated by the database; optimistic local ids are
  swapped for the server row after insert (see `createApp`).
- Every club-scoped table carries `club_id` and RLS scoped through
  `is_club_member` / `is_club_admin`.
- Status fields stay as data (`draft` / `published` / `archived`), never as
  deletion.
- Never widen a store's API to expose Supabase details — if the UI needs to
  know, that is a bug in the repository boundary.
